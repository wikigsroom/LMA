## 使用逻辑

1. 在“全部 / HF 搜索”打开所需仓库的文件，选择“构建本地模型配方”，再选择架构配方。保留原有“推荐”、所有模型平级及“生文 / 生图 / 生视频 / 生音频”和基座依赖标签。
2. 可先手动选择主组件，再点击“检查配套文件”。检查当前文件页面所属仓库的**同一固定提交**，包括后续目录页；只读取目录元数据，不下载模型。主组件并非检查的前置条件，唯一文件也可以先建议、由用户确认。
3. 查看仓库、提交、角色、路径、大小及文件校验信息。Sana 的 MNN 图与 `.weight` 按完整路径配对；同名文件分布在两个目录时保留为多个候选，不根据列表顺序猜选。已有手动绑定保持原样。
4. 勾选需要应用的唯一建议并确认。必需组件默认勾选，可选组件默认不选。取消勾选的必需项仍然缺失，模型不能提前登记。不能通过提交任意文件信息或旧表单覆盖已有绑定。
5. 补齐仍需手动选择的组件。多仓库模型可在组件选择器切换仓库，返回后分别检查各固定版本；每个绑定保留自己的来源。只有全部必需组件已选，才可点击“加入本地并查看下载计划”。
6. 登记后的模型仍未安装。用户查看完整计划、复用空间和许可后，另行点击下载。下载 / 暂停 / 续传 / 导入 / 删除、独立参数、任务和产物继续使用已有共用流程。

目录较大而未检查完整时，页面会明确说明并禁用建议应用；不能把部分目录中的一个文件说成整个仓库唯一。网络错误可返回重试或手动选择；“停止检查”使后续目录检查停止、旧结果失效。已经发出的目录请求可能先完成，结果不会重新写回已停止或已切换的配方。

## 覆盖与限制

当前保留 **35 套配方**，其中 **19 套具有 57 条声明式文件匹配提示**。包括 Sana Edit 的 15 个组件、Nano 完整方案的文件名、Kokoro / Piper / Matcha / Qwen TTS 的匹配文件、OpenMOSS extras 和部分生图 / 视频配方的标准配套文件。其余角色继续使用手选，不根据扩展名自动认定配套关系。

这些数字描述选择流程与文件名规则，**不代表 35 套模型已经通过实际推理或 Android 验收**。命名相符仍需核对模型架构、同次导出、量化、codec、分词器、许可和设备资源；不自动获得源模型的其他能力，也不会将用户配方提升为已核对的无审查条目。

| 情况 | 行为 |
|---|---|
| 同一固定目录中一个明确文件匹配 | 展示建议，等待用户勾选确认 |
| 多个匹配、同名不同目录、跨角色重复文件 | 保留手动选择，不猜选 |
| 目录未完整读取 | 不声称唯一，不应用建议 |
| 已有手动选择 | 保留；建议不覆盖 |
| 配方、绑定或检查结果已变化 | 旧确认失效，重新检查 |
| 缺件、缺引擎、访问受限或资源不足 | 本机说明原因，不补下载、不使用其他设备推理 |

## 基座实现与证据

`RecipeSuggestions` 使用配方内的 `matchFiles` / `matchSibling` 数据；页面、队列和控制器没有按具体模型 ID 新增分支。`HubClient.inventory` 沿用生产 HF 元数据与固定提交分页校验，限制最多 8 页 / 2,048 个候选，拒绝重复路径、重复游标、混合来源 / 提交、受阻文件及不合法匹配规则。

建议保存在短期草稿中，以原生检查 ID 和绑定指纹校验。确认只提交角色列表，实际文件从原生已检查的结果解析；随后仍需单独登记与下载。匹配提示从模型身份计算中剔除。dev.36 的 Sana 图片编辑是与旧文生图声明不兼容的新配方，必须明确选择，并有独立身份；旧 dev.33 的 13 组件 manifest 仍可完整读取，不自动迁移或改写其设置和任务。

[生产检查](../verification/development/recipe-suggestions.json) 使用真实生产 Java 客户端、控制器与持久存储，HTTP 元数据和文件内容为明确夹具。覆盖分页、15 组件、歧义、配对路径、显式合并、旧身份、停止、变更、错误和零资产下载。既有 HF / 后端回归也保留当前记录；这些检查均不执行模型。
