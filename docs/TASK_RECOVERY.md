# 任务恢复、容量与历史管理

[English](TASK_RECOVERY.en.md) · [文档目录](README.md) · [本轮编号交付与全部待办](releases/v0.3.0-dev.27.md)

内部开发 **0.3.0-dev.27 / code 31**。这是共用任务基座的功能更新，沿用所有模型平级、独立参数、不可变请求、单手机执行和用户自主管理资产的要求。没有新增模型权重，没有新的模型推理或 Android 验收通过项。

## 1. 用户使用流程

1. 在“任务”页查看中断检查提示、任务记录 / 待处理 / 素材与结果的容量。应用启动时检查上次保存状态；不会因为检查而下载模型或重新生成。
2. 通过“全部 / 进行中 / 已完成 / 中断失败”筛选任务，搜索模型名、模型 ID、任务 ID 或提示词摘要。默认显示最新 20 条，“显示更多”每次增加 20 条；筛选与搜索可以组合。
3. 找回已保存结果的任务仍显示“已中断”和恢复说明，详情保留原错误并提供结果入口。可查看、导出结果，或编辑原请求后明确提交新任务；不会冒充自动续步或生成成功。
4. 点击“清理已结束记录”，检查记录清单，勾选确认后清理。本次检查之后才结束的任务保留；如果所选记录被其他操作改变，整批拒绝，需重新检查并确认。
5. 清理只删除所选终态任务记录及其幂等键。结果文件、来源、草稿、模型、独立设置、排队 / 运行任务保留。已有结果仍可恢复生成输入。删除结果文件需另行主动操作。

## 2. 启动对账与临时文件

初始化顺序为：持久任务恢复 → 结果库 → 可续传输入恢复 → 已提交结果对账 → 引擎工作目录恢复 → 接纳服务 / 工作线程。恢复检查拒绝活动任务或正在读取的结果库。

`JobStore` 将原 loading / running 任务改为 interrupted，将 cancelling 改为 cancelled；没有引擎 checkpoint 时不声称可以续步。`ArtifactStore.reconcile` 以已提交的私有索引为依据，检查文件存在及大小。对于没有结果链接的 interrupted 生成任务，只有结果来源为生成、执行来源为本机、完整请求与原不可变请求相同、模型包 ID 一致时才追加链接，写入 `output_recovered` 事件。已链接结果不重复追加；取消任务不复活。来源不匹配和丢失文件保留记录并报告问题。

启动检查不会重新完整哈希大型文件，不重新执行推理。它恢复的是已提交索引中的记录关联，不能证明同大小文件未被修改，也不能恢复尚未提交的结果。作为后续参考素材时，实际执行仍按原有规则重新核验选定文件的完整哈希。

仅回收应用结果目录内、命名符合生成器规则的普通文件：`staging/job_<32hex>_<32hex>.<suffix>` 和未被索引引用的 `media/artifact_<32hex>.<png|jpg|wav|mp4|txt|json>`。不递归删除，不跟随符号链接，不扫描模型目录；索引结果、未知条目和已登记的续传输入保留。移动完成但索引未提交的文件属于未提交结果，会被回收；本轮没有新增跨库事务日志。删除失败会报告并留待下次启动检查。

`outputRecovery` 汇总找回、缺失、来源拒绝、未关联、临时回收和失败数，以及实际回收字节；`executionResumed` 与 `modelDownloads` 均为 false。历史清理后的无任务结果允许独立存在，不作为错误弹出。

## 3. 容量与提交逻辑

| 对象 | 上限 | 满额后的行为 |
|---|---|---|
| 持久任务记录 | 256 条，包含终态 | 提示检查并清理已结束记录，保留结果文件 |
| 待处理任务 | 64 条，含 queued / loading / running / cancelling | 等待结束或明确取消；清理历史不会取消活动任务 |
| 素材与结果索引 | 2,048 项 | 明确删除不需要的文件；清理任务历史不能释放此容量 |

页面 / API 的运行前检查与生成提交共用真实容量检查；检查只读，不预留名额。实际入队仍在持久队列中复查；已有幂等请求可以在历史满额时取回原记录。执行前和结果发布时复查结果库容量，已接纳队列不会仅因任务记录满额而停止启动。容量变化或另一请求可能使检查通过后的提交失败，必须以实际返回为准。

## 4. 本地 API

沿用密钥鉴权、请求体限制、同源约束和服务开关。API 与页面操作同一份原生存储：

| 方法 | 行为 |
|---|---|
| `GET /v1/jobs/history` | 只读返回终态 `ids`、`count`、`review` 与任务 `capacity` |
| `POST /v1/jobs/history/clear` | 提交 `{"ids":["任务ID"],"review":"检查返回值"}`；成功返回 `removed` 与最新 `capacity` |

客户端先取得完整计划，再把计划中的 `ids` / `review` 原样作为明确清理请求提交；不要把 `count` / `capacity` 加入清理请求。服务逐项核对终态、唯一 ID 及其状态 / 时间指纹，全部验证通过后才一次原子写入。变更返回 409，其他非法输入按既有规则拒绝。清理不生成任务、不启动引擎、不删除素材；成功后刷新 App。重复提交已删除计划也是冲突，不会扩大删除范围。原有单条终态删除仍可使用。

## 5. 检查与边界

`tools/test_recovery.py` 编译生产核心代码，在真实主机子进程完成结果提交后 `halt(37)`，父进程重启存储并核对输出字节、关联、事件和回收范围；同时使用真实持久文件和带鉴权 HTTP。不是模拟器或 Android 测试。生产调度套件补充满额运行前检查与只读验证；完整 UI 回归覆盖筛选、分页、确认、并发范围保留、冲突恢复及容量导航。
