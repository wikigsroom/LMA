# 共用执行槽、文本驻留与任务切换

[English](SCHEDULING.en.md) · [开发状态](DEVELOPMENT.md) · [任务方案](WORKFLOWS.md) · [API](API.md) · [模型资产边界](ASSET_CONTROL_AUDIT.md)

适用：**0.3.0-dev.10 / code 14，内部开发检查点**。常驻文本加载、应用内聊天、同步文本 API 与异步生成任务已接入同一个 `ExecutionGate`。完整 v0.3.0 的模型范围和物理 Android 验收仍须全部完成。

## 用户操作

1. 自行下载或导入所需模型，在“本地”选择并加载文本模型。没有模型仍能启动、浏览和管理 App。
2. 文本回复正在输出时，可以提交已安装模型的生成任务；任务显示“等待本机执行槽”，当前回复继续完成。
3. 轮到任务时，基座暂时卸载空闲文本进程，确认退出后重新检查资源，再启动所选任务的引擎。任务仍使用提交时保存的模型、LoRA 和参数快照。
4. 文本暂时卸载期间，仍可发送一条聊天或同步 API 请求；回复排队，轮到它时加载此前选择的文本模型。界面区分“回复已排队”和实际生成，并保留取消入口。
5. 任务队列空闲后恢复用户仍希望运行的文本模型。点击“停止文本模型”会撤销恢复意愿；当前独立任务继续。任务执行期间选择另一个已安装文本模型，会排队加载用户新选的模型。

此流程只复用已经安装的用户资产。App 不选择新模型、不下载缺失组件、不更换权重或转向其他设备。基座代码、引擎与调度随 APK 更新；模型仍由用户独立选择、下载和管理。

## 顺序、身份与参数

异步任务由 `JobStore` 按持久队列顺序领取；领取后与加载、聊天、HTTP 请求一起申请执行槽，**按执行槽申请顺序服务**。因此队列任务和连接请求的全局顺序以实际申请槽的时间为准。空闲自动恢复只在没有占用者和等待票据时原子预约，不插队或改变正在准备的请求代次。

常驻文本进程空闲时可以保留在内存；真正的聊天或 HTTP 响应持有执行槽，直到回复结束、取消或响应流关闭。其他引擎必须先回收旧进程。基座默认只有一个大型引擎进程，不因不同模型使用不同原生模块而并行抢占内存。

原文本 ID、不可变 `bundle_id`、推荐、标签和独立配置不变。API 请求在排队前按当时选定模型和配置规范化；排队不会替换目标模型。应用内聊天也保存原请求和对应历史。已有一个应用内或同步 API 回复正在输出或等待时，另一条交互式文本请求会报告忙碌；异步生成仍可独立排队。

## 取消、停止与进程回收

| 操作 | 行为 |
| --- | --- |
| 取消等待的异步任务 | 撤销该任务票据，不启动引擎、不停止正在输出的文本 |
| 取消等待的聊天 / API | 释放对应票据；聊天保存“已停止”；独立任务继续 |
| 停止文本模型 | 取消延迟加载和恢复意愿，终止该文本进程；独立任务不受影响 |
| 关闭 API 监听 | 关闭连接、取消等待的文本请求；已启动异步任务继续 |
| 停止整个服务 | 取消文本、停止任务工作进程，任务明确记为中断；已有模型、配置与结果保留 |

取消以票据和进程代次区分归属，旧响应的迟到清理不能释放新请求。监听关闭或服务端连接保护超时时会中断相应处理线程，唤醒等待者。客户端自身超时可能早于手机端排队结束；需要可靠后台结果的调用方应使用异步任务接口。

进程先正常终止，必要时强制终止，分别最多等待三秒。如果操作系统尚未回收工作进程，执行槽显示 `reaping`，仍保留模型租约和临时文件；实际退出后才释放。后续操作等待，不启动第二个大型引擎。常驻文本模型的资产租约同样保留至真实进程退出。

原生文本进程意外退出继续使用最多三次的有限恢复，恢复也要申请执行槽。已停止、更换或取消的旧代次不能重新启动。

## 资源与生命周期

提交阶段根据设备总内存与保留量检查已知容量，并核对组件、参数和磁盘预算；不把当前文本驻留占用当作永久不可用容量。真正取得执行槽并回收旧进程后，再读取可用共享内存、低内存和温度状态，执行同一配方预算检查。未知资源估算仍需用户明确允许尝试，设备实测档案尚未建立。

单任务两小时保护从取得执行槽、回收旧引擎和取得模型租约之后开始，覆盖实际生成，不计排队等待。文本加载另有五分钟保护。锁屏运行依赖原生前台服务和系统策略；本检查点没有新增真机耐久保证。

异步任务保存请求、有效参数、状态、事件和结果；聊天保存 SQLite 历史及已收到的片段。进程重启后，对没有 checkpoint 的中断任务明确重试，不能假装从中间采样步续算。传输保持暂停，只有用户点击继续才恢复。

## 实现与证据

`ExecutionGate` / `ProcessControl` 管理执行槽与退出边界；`EngineHost` 管理文本驻留和有限恢复；`LocalJobs`、`ChatRunner`、`ApiHost` 使用同一个槽。所有原生启动还受 `nativeProcessLock` 和实际子进程存活检查保护。`/health` 的 `scheduler` 与 App 状态的 `foundation.execution` 提供真实占用和等待信息。

运行 `python tools/test_scheduler.py` 可复查 **43 项主机检查**，包含生产队列 / 聊天 / API、真实子进程与回环 HTTP、取消、延迟进程回收、独立服务停止、资源准入和原配置保留。框架、资源和媒体探测是明确的主机适配端口，GGUF 为零张量元数据，输出为任意测试字节或固定文本；没有执行模型推理或 Android。
